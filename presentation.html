What it does It watches, enriches, classifies, and reports.

The agent does not fix the Flow. It reads signals, explains what happened, and guides the operator.

System output Alert in console or Slack

The default Alert Sender prints to the console. Slack is used only when it is turned on on purpose.

Safety Read first, control only by rule

The monitor is read-only. Flow controls in Slack are a supervised exception from ADR 0007, with a dedicated key.

The flow path

This is the main path to explain. The read is deterministic until the classification step, and the output stays controlled.

1

Watch Flows

The agent scans the Flows it tracks and reads health, run state, and volume signals.

2

Find Anomaly

It marks the first signal as Explicit Failure, Silent Failure, or health_sweep.

3

Do Enrichment

It gathers what is needed to understand the case: Flow state, last run, counts, and useful log lines.

4

Build Evidence

It arranges the data in a clean form so the LLM can decide with more context and less noise.

5

Set Risk Classification

The LLM returns low, high, or uncertain. If it is uncertain, it is handled as high.

6

Send Alert

The Alert includes a direct explanation and a Recommended Action, with a Suppression Window to avoid repeats.

One pipeline, three entry points

Detect → Enrich → Classify → Alert is shared. The Scheduler and Monitoring run it on the timer; a Scan triggers it by hand. Only the Scheduler suppresses repeats — Scan and Monitoring are meant to report.

Types of Anomaly

A simple table helps in the talk. Each type starts from a different signal and needs a different focus.

Type How it shows up What it means How to explain it
Explicit Failure Nexla already reported it, and the agent already handled that signal. The Flow got a clear failure signal. "The system said it clearly. The agent organizes it, adds Enrichment, and points the way."
Silent Failure The Flow runs, but it processes 40% or more fewer records than at the same time yesterday. Volume is lower, but there is no clear message from Nexla. "Nothing looks broken at first, but the output dropped too much."
health_sweep The org health sweep finds a Flow in RED with no signal already handled. A bad state was found that was not covered before. "It is a safety sweep so a red Flow does not get missed."
Practical read

Explicit Failure

It often gives enough detail to start the talk, but it still goes through the same Enrichment and Evidence path.

Volume

Silent Failure

This is the most useful read when the Flow looks normal but the output dropped hard.

Coverage

health_sweep

It closes gaps: if the Flow is RED and no signal is already handled, the agent speaks up.

Enrichment and Evidence

This step is good to show because it separates “spot something” from “know enough to decide.”

Enrichment

It collects the signals that give shape to the Anomaly: Flow health, last run, record count, count of bad lines, and useful log lines. The goal is less guesswork.

Evidence

This is the final packet for the LLM: organized data, clear facts, and easy comparisons. Better Evidence leads to better Risk Classification and a better Recommended Action.

Risk Classification via LLM

The LLM does not replace the signals. It judges how much attention the case needs and returns a simple answer.

low

Low

The signal is clear, there is enough Evidence, and the case looks contained. The Alert can stay short and direct.

uncertain

Gray zone

If the answer is not clear, it is handled as high. This avoids undercalling a Flow that needs human review.

high

High

There are strong signs of impact or volume loss. The message must be direct and the Recommended Action must be clear.

How to say it in the talk

“The deterministic part finds the Anomaly. The LLM helps read the Evidence and pick what the operator should check first.”

Noise control and delivery

It is worth saying that the agent tries to be useful without sending the same Alert again and again.

Suppression Window

Keeps repeats out

By default, the agent does not send another Alert for the same Flow and the same Anomaly type during the set window.

Blocklist

Stops chronic noise

Noisy Flows can go on the Blocklist so they do not burn attention with too many messages.

Alert Sender

Console or Slack

The default sender writes to the console. The Slack sender is for supervised use and does not change the read-only nature of the monitor.

ADR 0007 exception

Supervised Slack controls

Flow controls in Slack are an explicit exception, with a dedicated key and supervision. This is not the normal path.

Demo and talking points

Use this section as a short talk track. It works well when you move between the page and a terminal/log view.

1

Start with the goal: “This agent watches Nexla Flows and turns weak signals into a useful Alert.”

2

Show the path: read → Anomaly → Enrichment → Evidence → Risk Classification → Alert.

3

Explain the cases: Explicit Failure, Silent Failure, and health_sweep start in different ways, but they follow the same path.

4

Talk about safety: the monitor is read-only; Slack controls are supervised and not the default.

5

Talk about noise: Suppression Window and Blocklist help avoid repeats and operator fatigue.

6

Close with value: less noise, clearer reads, faster human response, and better focus on what matters.

Close

If people remember one thing, let it be this: the agent does not try to do everything. It tries to make each Flow easy to read, trust, and act on.

Final note

The agent combines deterministic reads, well-chosen Enrichment, and an LLM to set Risk Classification with more context. The result is a clear Alert with controlled noise and safe output.
