# Redact credentials from error text before it reaches the Alert sender or the LLM

The agent masks credential and connection-string patterns in Nexla-sourced free text — the anomaly `message`, the flow `errorSummary`, and the top error log lines — before that text is emitted through the Alert sender or sent to the opencode.ai LLM. Masking happens in one small module, `modules/redaction.py`, applied at the enrichment step (for Evidence fields) and at the two consumption boundaries (the Alert builder and the LLM payload).

The TDD's security notes warn that "Nexla error messages may contain table names or connection strings" and that such content "must be logged at DEBUG level only, never at INFO or above in production." The adapter already honors this — every SDK exception is logged at DEBUG (ADR-context: see `nexla_adapter.py`). But two paths deliberately surface error text at a higher visibility than DEBUG, and a code review flagged both:

1. **The Alert sender** (`sender.send(build_anomaly_alert_text(...))`) emits `message`, `error_summary`, and `top_error_logs` on every alert. The current destinations are console output by default and Slack when explicitly enabled, so a connection string embedded in a Nexla error could land in the container console, a log aggregator, or the configured Slack channel.
2. **The LLM call** sends the same fields off-platform to opencode.ai inside the classification payload.

Sending error text to the LLM is **intentional and load-bearing**: the agent's whole job is to read a failure's details and explain it in plain language ([ADR-0002](0002-deterministic-detection-llm-classification.md) — the LLM classifies and explains after deterministic detection). We cannot simply stop sending error context. What we *can* do is strip the parts that are sensitive and add nothing to an explanation — embedded credentials and connection URLs.

`redact()` masks: credentials embedded in URLs (`scheme://user:pass@host` → `scheme://***:***@host`), JDBC connection strings (`jdbc:...` → `jdbc:***`), and `password=` / `pwd=` / `secret=` / `token=` / `api_key=` / `access_key=` style key-value secrets. It deliberately leaves the rest of the message intact (table names, error codes, stack context) because that material is what makes the LLM explanation and the operator Alert useful, and masking it would defeat the agent's purpose.

This keeps redaction as business logic in the Modules layer, consistent with the architecture: detection, enrichment, classification, and alerting are all modules, and redaction is a small shared module they call.

**Consequence**: error text shown in Alerts and sent to opencode.ai is masked for credentials, reducing (not eliminating) the blast radius of a leaked secret. Residual risk remains and is accepted for v1: (a) the redaction is pattern-based, so a credential in an unusual format can still pass through; (b) non-credential sensitive data (table names, internal hostnames not in a URL) is intentionally **not** masked, because it is part of the explanation the agent exists to produce; (c) the LLM egress itself is an accepted data-sharing decision — error context is sent to a third-party model by design. If stricter guarantees are needed later, options are an allowlist-based summarizer before egress, a self-hosted model, or operator-configurable redaction rules.

**Considered Options**: (1) *Do nothing — accept that error text flows to Alert destinations and the LLM* — rejected; embedded credentials are a real, avoidable leak and the review flagged it. (2) *Stop sending error text to the LLM* — rejected; it removes the signal the LLM needs to classify and explain, defeating ADR-0002's design. (3) *Route the Alert through `logger` at DEBUG instead of the Alert sender* — rejected for v1; the Alert is the product's primary operator output and hiding it at DEBUG defeats the agent's purpose. Redaction addresses the leak without hiding the Alert. (4) *Mask everything that looks like infrastructure (all hostnames, all identifiers)* — rejected; it would strip the very context that makes the Alert and explanation actionable, and over-redaction trains operators to ignore Alerts.
