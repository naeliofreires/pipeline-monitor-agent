# Keep alert state in SQLite to suppress repeat alerts and honor a Blocklist

The agent remembers which flows it has already alerted on, in a local SQLite database, and refuses to re-alert the same `(flow_id, anomaly_type)` again until a Suppression Window has passed. It also reads a Blocklist from `config.yaml` and never alerts on flows the operator has listed there. Both checks run in code, before enrichment and the LLM call, so a suppressed or blocklisted problem costs no Nexla read calls and no LLM spend.

Until now the only dedup the agent had was Nexla's own notification `read` flag: after handling an Explicit Failure, the agent marks the notification read so it is not fetched again. That works for notification-driven anomalies, but the org health sweep ([ADR-0003](0003-enrich-anomalies-before-classification.md) added it as `health_sweep`) has no such flag. A flow that stays RED is returned by `flows.get_org_health_flows(health_status="RED")` on *every* tick, so the agent would re-detect it, re-enrich it, re-classify it, and re-emit the same Alert every 5 minutes for as long as the flow stays broken. The sweep we added to widen coverage also created a new, recurring source of alert noise — exactly the failure mode the TDD's Suppression Window was meant to prevent. The same will be true of Silent Failures (v1), which are volume-derived and likewise have no Nexla-side read flag.

This introduces the third project layer, **Repositories** — the only code that touches SQLite. Detection stays deterministic ([ADR-0002](0002-deterministic-detection-llm-classification.md)) and the agent still never acts on a flow ([ADR-0001](0001-read-only-agent.md)); suppression only decides whether an already-detected Anomaly is *worth alerting on again*, it never changes flow state.

The state we keep is deliberately small:

- `suppression(flow_id, anomaly_type, alerted_at, suppressed_until)` — one row per Alert actually emitted. `is_suppressed` is a single indexed lookup for a live row (`suppressed_until > now`); `record_alert` inserts a row with `suppressed_until = now + suppression_window`.
- The Blocklist is not state — it is operator config (`blocklist:` in `config.yaml`, a list of `flow_id` with a `reason`), checked in the same module before the suppression lookup.

**Consequence**: the agent now carries persistent local state, so the SQLite file must outlive the container. `docker-compose.yml` mounts a named volume at `/app/data`; if that volume is lost, the Suppression Window resets and the next tick may emit a burst of repeat alerts (annoying, never wrong — the agent only watches). Suppression keys on `flow_id`, so an Explicit Failure whose `resource_id` could not be resolved to a flow (`flow_id is None`) is not suppressed by this layer — it still relies on the Nexla `read` flag, which already covers it. The window is a fixed duration per `(flow_id, anomaly_type)`; a flow that is still broken after the window legitimately re-alerts, which is the intended reminder behavior. SQLite is opened and closed once per tick, single-threaded, so there is no concurrency concern. Alert delivery destination does not change these semantics: console and Slack emitters both receive only Alerts that pass Blocklist and Suppression Window checks.

**Considered Options**: (1) *No state — re-alert every cycle, rely only on the Nexla `read` flag* — rejected; it does not cover the `health_sweep` or future Silent Failures and floods the console for any persistently broken flow. (2) *Keep the suppression set in memory* — rejected; it resets on every container restart, so a restart loop becomes an alert loop, and there is no audit trail of what was alerted when. (3) *Use an external store (Redis/Postgres)* — rejected as over-built for a single-container dev/prototype agent; SQLite on a mounted volume is enough and adds no new infrastructure. (4) *Put the SQLite calls in the suppression module* — rejected; that module is business logic and, like detection and classification, must not talk to storage directly. SQLite access lives in the Repositories layer and is injected into the module, mirroring how adapters are injected into detection and enrichment.
