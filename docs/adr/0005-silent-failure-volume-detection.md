# Detect Silent Failures by day-over-day volume comparison

The agent detects **Silent Failures** — flows that still look healthy (no failed run, no notification) but have processed dramatically fewer records than usual. Each tick it reads every flow's record volume for today's date window and compares it to the same flow's volume for yesterday's window; if today's volume has dropped by at least a threshold (default 40%), it raises a `silent_failure` Anomaly that flows through the same enrich → classify → alert → suppress pipeline as every other anomaly.

Until now the agent only saw problems Nexla already considered problems: unread notifications ([ADR-0002](0002-deterministic-detection-llm-classification.md)'s `explicit_failure`) and RED org-health flows (`health_sweep`). Both are *loud* failures — something errored. The TDD's motivating problem is the *quiet* one: "a flow that processes 95% fewer records than yesterday does not trigger any alert; the problem only shows up later when downstream data is out of date." A flow can stay GREEN, finish its run successfully, and still be silently broken upstream (an empty source extract, a filter that now matches nothing, a credential that returns an empty page instead of erroring). Volume is the only signal that catches this, and detecting it is what completes Level 3 (proactive detection) of the maturity roadmap.

Detection stays deterministic ([ADR-0002](0002-deterministic-detection-llm-classification.md)): code does the volume math and decides what is anomalous; the LLM is still only called afterward to classify severity and write the explanation. The agent still never acts on a flow ([ADR-0001](0001-read-only-agent.md)) — a Silent Failure produces an Alert, nothing more.

**Where the baseline comes from.** Nexla's org-health endpoint (`flows.get_org_health_flows`) accepts a `from_date`/`to_date` window and returns, per flow, the `origin_node_id`, `healthStatus`, and `latestRecordCount` for that window. So "volume in the current window vs the same window yesterday" is two read calls — today's window and yesterday's window — with no warm-up period: Nexla already retains the history. The new **`metric_snapshots`** repository persists each tick's observed per-flow volume so the comparison survives even when yesterday's window cannot be re-read (API gap), and so a future rolling-average baseline (7+ days, out of scope for v1) has data to build on. The repository is therefore the durable record and the resilience fallback; the live API window is the primary baseline.

The state we keep is small and append-mostly:

- `metric_snapshots(flow_id, window_start, record_count, captured_at)` — one row per `(flow_id, window_start)` date, upserted each tick. `get_record_count(flow_id, window_start)` is the indexed baseline fallback; `purge_older_than` drops history past a retention horizon so the file stays small.
- Suppression of repeat Silent Failure alerts reuses the existing `suppression` table ([ADR-0004](0004-sqlite-state-suppression-window.md)) keyed on `(flow_id, 'silent_failure')` — a flow whose volume stays low is alerted once per Suppression Window, not every tick.

**Guards against false positives.** A drop is only flagged when the baseline is at least `min_baseline_records` (default 100) — tiny or brand-new flows have too much natural variance to alert on. The threshold is configurable globally (`detection.volume_threshold_pct`) and per flow (`detection.flows[].volume_threshold_pct`) so an operator can loosen it for a known-spiky flow instead of blocklisting it outright. Flows already raised this tick as an Explicit Failure or `health_sweep` are excluded — a RED flow's low volume is a symptom of the failure already being reported, not a separate Silent Failure.

**Consequence**: detection now costs two extra read calls per tick (today's and yesterday's volume windows) regardless of how many flows exist, plus one snapshot upsert per active flow. The whole Silent Failure sweep is wrapped so that any failure to read volumes degrades to "no Silent Failures this tick" and never blocks Explicit Failure or health-sweep alerting. The comparison is day-granular: early in a UTC day, today's partial window is compared against yesterday's same partial window as Nexla reports it — if Nexla's `latestRecordCount` over a `from`/`to` window turns out to mean something other than "records in that window," the threshold may need tuning against real data (tracked as a validation gap). The `metric_snapshots` file shares the same SQLite database and Docker volume as `suppression`; losing the volume only resets the snapshot history, and the live API baseline still works.

**Considered Options**: (1) *Snapshot-only baseline — store volume each tick and compare to our own snapshot from ~24h ago* — rejected as the primary path because it is blind for the first full day of operation and a restart that loses the volume re-blinds it; kept instead as the durable fallback. (2) *Per-flow daily metrics via `metrics.get_resource_daily_metrics`* — rejected for the sweep because it is one call per resource (sources/sets/sinks) across every flow, far more expensive than the two org-health window calls, and it forces resolving each flow to a representative volume-bearing resource. (3) *Rolling 7-day average baseline* — deferred; the TDD puts it out of scope for v1 (needs a week of history), and simple day-over-day is enough to close Level 3. (4) *Put the volume math or the SQLite access in the same place* — rejected; volume comparison is business logic and lives in `modules/detection/silent_failure.py`, SQLite lives in `repositories/snapshot_repository.py`, and the org-health read lives in the Nexla adapter, mirroring the existing layering.
